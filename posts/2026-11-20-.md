When I first started writing production‑grade Node.js services, I thought I had a solid grip on async/await. I’d read the docs, watched a couple of tutorials, and felt confident enough to sprinkle `try/catch` blocks everywhere. Fast‑forward a few weeks, and I was staring at a cascade of “UnhandledPromiseRejectionWarning” messages in my logs, each one pointing to a different corner of the codebase. It felt like the universe was playing a cruel joke: *“You thought you knew async? Think again.”*  

In this post I’ll walk you through the exact scenario that broke my night, the misconceptions that led me there, and a reusable pattern that finally gave me peace of mind. By the end you’ll know:

* Why a simple `try/catch` around `await` isn’t enough for every case.  
* How to centralize async error handling without turning your code into a spaghetti mess.  
* A practical helper function you can drop into any project today.

## The Night the Server Went Silent

It was a rainy Tuesday, and the new “order‑processing” endpoint was about to go live. The route looked clean:

```js
// src/routes/orders.js
router.post('/process', async (req, res) => {
  const { cartId } = req.body;
  const cart = await CartService.getCart(cartId);   // ← async
  const payment = await PaymentGateway.charge(cart); // ← async
  await NotificationService.sendConfirmation(cart.userId); // ← async
  res.status(200).json({ success: true });
});
```

All the calls returned promises, and I wrapped each with `await`. I felt safe—if any of those promises rejected, the `await` would throw and the `express` error‑handler would catch it.

But the night the endpoint went live, the logs were full of this:

```
(node:12345) UnhandledPromiseRejectionWarning: Error: Payment declined
    at ...
    at process._tickCallback (internal/process/next_tick.js:68:7)
```

Why wasn’t my global error handler catching this? Turns out the culprit was **not the `await` statements**, but a tiny helper I’d written earlier:

```js
// src/utils/asyncWrapper.js
module.exports = fn => (req, res, next) => {
  fn(req, res, next).catch(next);
};
```

I used it to wrap route handlers, *except* for this one. I’d forgotten to export the router with `asyncWrapper`. So the promise chain was left dangling, and Node emitted the unhandled rejection warning instead of bubbling the error to Express.

## The Core Misconception

Many devs (myself included) treat `try/catch` as a silver bullet for async errors. That works **inside** an async function, but as soon as you leave the async context—like a promise returned from a library or a callback that isn’t awaited—the error can slip through.

Two common patterns that cause trouble:

| Pattern | Why it fails |
|---------|--------------|
| **Fire‑and‑forget `await` inside a `try` block** | If you call `someAsync().then(...).catch(...)` *outside* the `try`, the `catch` is separate from the `try`. |
| **Returning a promise without awaiting it** | Express (or any framework) will treat the returned promise as “handled” only if you explicitly pass it to a wrapper that forwards rejections. |

The lesson: **You need a consistent boundary** where all async rejections are either awaited or explicitly forwarded to your error‑handling middleware.

## A Simple, Reusable Pattern

I settled on a pattern that couples three ideas:

1. **Universal async wrapper** for every route/controller.  
2. **Central error‑handling middleware** that formats and logs.  
3. **A “safe‑await” helper** for fire‑and‑forget tasks that still report failures.

### 1. The Universal Async Wrapper

```js
// src/middleware/asyncHandler.js
const asyncHandler = fn => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

module.exports = asyncHandler;
```

Notice the `Promise.resolve`—it works whether `fn` returns a promise or a plain value. Now every route can be declared like:

```js
const asyncHandler = require('../middleware/asyncHandler');

router.post(
  '/process',
  asyncHandler(async (req, res) => {
    const { cartId } = req.body;
    const cart = await CartService.getCart(cartId);
    const payment = await PaymentGateway.charge(cart);
    await NotificationService.sendConfirmation(cart.userId);
    res.json({ success: true });
  })
);
```

No more “did I forget to wrap this?” anxiety.

### 2. Central Error Middleware

```js
// src/middleware/errorHandler.js
module.exports = (err, req, res, _next) => {
  console.error(`[${new Date().toISOString()}]`, err);
  const status = err.status || 500;
  const message = status === 500 ? 'Internal Server Error' : err.message;
  res.status(status).json({ error: message });
};
```

Plug it at the very end of the middleware stack:

```js
app.use('/api', router);
app.use(require('./middleware/errorHandler'));
```

Now any rejection that reaches `next(err)` gets a clean JSON response and a timestamped log.

### 3. Safe‑Await for Fire‑and‑Forget

Sometimes you truly want “fire‑and‑forget”, e.g., logging to an external analytics service. You still want to know if it crashes.

```js
// src/utils/safeAwait.js
async function safeAwait(promise, onError = console.error) {
  try {
    await promise;
  } catch (e) {
    onError(e);
  }
}
module.exports = safeAwait;
```

Usage:

```js
await safeAwait(AuditLog.record('order_processed', { cartId }));
```

If the audit service is down, you’ll see the error in the console, but your request flow won’t be interrupted.

## Real‑World Refactor: From Panic to Confidence

After the rainy night, I rewrote all my routes with the `asyncHandler`. The transformation was surprisingly quick—most files only needed a single import and a wrapper. The next time we added a new webhook endpoint, the pattern was already baked in, and the test suite caught a typo before it hit production.

The biggest win? **No more “UnhandledPromiseRejectionWarning”** in our logs. Instead, every error is either:

* Propagated to the centralized handler (client‑visible, logged), or  
* Swallowed deliberately with `safeAwait` (internal, logged).

## Common Pitfalls Even With the Wrapper

1. **Mixing callbacks and promises** – If a library still uses Node‑style callbacks, wrap it with `util.promisify` or manually return a promise.  
2. **Returning early without awaiting** – `return res.json(...)` is fine, but don’t write `await something; return;` inside the same block without the wrapper; the wrapper still catches the rejection.  
3. **Forgotten async middleware** – Remember that any custom middleware that performs async work must also be wrapped or return a promise.
