## Why memory leaks matter

If you’ve ever watched a Node service grind to a halt after a few hours of traffic, you’ve probably felt the frustration of a memory leak. The process starts out fine, but slowly it starts to consume more RAM, GC pauses get longer, and eventually the OS kills the container. It’s a silent killer that can turn a healthy microservice into a costly outage.

In JavaScript we often assume the garbage collector (GC) does all the heavy lifting, but the GC only frees objects that are **no longer reachable**. When references linger—by accident or design—those objects stay alive forever, and the heap balloons.

## The story: “The mystery of the disappearing server”

A few months ago I was on‑call for a real‑time analytics platform built with Node.js and Socket.io. One evening, the dashboard started stalling for a handful of users, and the logs showed “Out of memory” errors. A quick `docker stats` confirmed the container was using 3 GB of RAM (our limit was 2 GB). The codebase was clean, tests passed, and the issue only manifested after the service had been running for ~6 hours.

My first instinct was to look at the recent code changes. Nothing obvious. Then I remembered a similar incident a year earlier where a stray event listener was the culprit. I decided to treat this as a classic “leaky listener” case and started digging.

## Common culprits in JavaScript

Before diving into tools, it helps to know the usual suspects:

| Culprit | Why it leaks |
|--------|--------------|
| **Event listeners** attached to long‑lived objects (e.g., `process`, `window`) but never removed. |
| **Timers** (`setInterval`, `setTimeout`) that keep a closure reference alive. |
| **Caches** that grow unbounded (e.g., storing request bodies in a global Map). |
| **Closures** that capture large objects unintentionally. |
| **DOM references** (in browser) held by detached elements. |

In a server‑side context, the first three are the most common.

## Diagnosing the leak

### 1. Reproduce locally with a memory‑profile flag

Node ships with a built‑in inspector. Running the service with `--inspect --expose-gc` lets us trigger manual GC and capture heap snapshots.

```bash
node --inspect --expose-gc index.js
```

Then I opened Chrome (`chrome://inspect`) and attached to the process. The “Memory” tab lets you take **Heap Snapshots** and **Allocation Timelines**. I took a snapshot after startup (baseline) and another after the service had been running for 30 minutes.

### 2. Compare the snapshots

Chrome shows a “Comparison” view that highlights objects whose retained size grew the most. The top offender was a `Map` called `socketUserMap` that kept growing by ~5 KB per minute.

```js
// Somewhere in src/socket.js
const socketUserMap = new Map();

io.on('connection', socket => {
  // Store user info for quick lookup
  socketUserMap.set(socket.id, { userId: socket.handshake.query.id });
  // ... other listeners ...
});
```

I realized I never removed entries when sockets disconnected.

### 3. Verify the leak with forced GC

Adding a quick endpoint helped confirm the hypothesis:

```js
app.get('/leak-check', (req, res) => {
  if (global.gc) {
    const before = process.memoryUsage().heapUsed;
    global.gc(); // force garbage collection
    const after = process.memoryUsage().heapUsed;
    res.json({ before, after, diff: before - after });
  } else {
    res.status(500).send('Run Node with --expose-gc');
  }
});
```

Calling `/leak-check` repeatedly showed the heap used never dropped after a disconnection, confirming the Map was holding onto dead sockets.

## Fixing the leak

The fix was straightforward: clean up the Map when a socket disconnects.

```js
io.on('connection', socket => {
  socketUserMap.set(socket.id, { userId: socket.handshake.query.id });

  // Listen for the disconnect event and clean up
  socket.on('disconnect', (reason) => {
    socketUserMap.delete(socket.id);
    console.log(`Socket ${socket.id} removed (${reason})`);
  });
});
```

I also added a defensive guard: if a socket ID was already present (unlikely but possible after a rapid reconnect), we overwrite the entry to avoid stale data.

```js
socketUserMap.set(socket.id, { userId: socket.handshake.query.id });
```

## Testing the fix

### Unit test for cleanup

```js
const { Server } = require('socket.io');
const io = new Server();

test('socket disconnect cleans map entry', done => {
  const client = require('socket.io-client')('http://localhost:3000');
  client.on('connect', () => {
    expect(socketUserMap.has(client.id)).toBe(true);
    client.disconnect();
  });

  client.on('disconnect', () => {
    expect(socketUserMap.has(client.id)).toBe(false);
    done();
  });
});
```

### Load test with `autocannon`

I ran a quick load test that opened 1,000 concurrent sockets for 5 minutes. After the run, the heap stayed flat around 250 MB—no more creeping upward.

```bash
npx autocannon -c 1000 -d 300 ws://localhost:3000
```

## Preventing future leaks

1. **Always pair listeners with cleanup** – whenever you `on` something on a long‑lived object, add a matching `off` or `removeListener` in the appropriate lifecycle hook.
2. **Wrap timers in a manager** – keep a registry of `setInterval` IDs and clear them on shutdown.
3. **Limit cache size** – use LRU caches (`lru-cache` npm package) to bound memory.
4. **Automate heap‑snapshot diffing** – CI can run a short‑lived script that takes two snapshots and fails if retained size grows beyond a threshold.
5. **Enable `--trace-gc` in staging** – gives you a quick view of GC frequency and pause times.

## Takeaway

Memory leaks in JavaScript are often the result of forgotten cleanup—event listeners, timers, or cached data that outlive their usefulness. By using Node’s inspector, taking heap snapshots, and systematically comparing object growth, you can pinpoint the offending reference quickly. The key habit is to **always pair allocation with deallocation**, even in a language that “does the GC for you.” Once you adopt that discipline, your services stay healthy, your containers stay within limits, and you’ll spend far less time firefighting OOM crashes. Happy debugging!
