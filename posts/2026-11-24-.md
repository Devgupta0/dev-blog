## The Moment It All Went Wrong

It was a typical Tuesday morning: coffee, a quick stand‑up, and then the usual “ping” from our monitoring dashboard. Our `order‑service`—a tiny Node.js microservice that lives behind an API gateway—was spiking memory usage. The heap was hovering around 1.2 GB on a container that only had 1 GB of RAM allocated. Within minutes the container was OOM‑killed and the whole order flow stalled.

I’d seen memory alerts before, but never at this scale. The logs didn’t show any errors, and the service was otherwise healthy. I knew I had to dig in fast, because every order that failed meant lost revenue and angry customers.

## Diagnosing the Leak

The first thing I did was reproduce the problem locally. I spun up the same Docker image and fed it a synthetic traffic pattern that mimicked the production load. The memory usage grew steadily, even after the traffic stopped. That confirmed it wasn’t a sudden burst—something inside the process was holding onto references.

I started by adding a few `process.memoryUsage()` logs at strategic points:

```js
function logMemory(label) {
  const { rss, heapTotal, heapUsed, external } = process.memoryUsage();
  console.log(`[${label}] RSS: ${(rss/1e6).toFixed(2)} MB | HeapUsed: ${(heapUsed/1e6).toFixed(2)} MB`);
}

// Example usage
logMemory('startup');
// ... later in request handler
logMemory('after request');
```

The numbers were eye‑opening: each request added roughly 5 MB of `heapUsed`, and the growth never reversed. That’s a classic sign of a leak—objects are being allocated but never released.

## Profiling with Chrome DevTools

Node.js ships with the `--inspect` flag, which lets you attach Chrome DevTools to a running process. I started the container with:

```bash
node --inspect=0.0.0.0:9229 server.js
```

Then I opened `chrome://inspect` in Chrome, connected to the remote target, and took a heap snapshot after a few hundred requests. The snapshot showed a massive number of `Map` entries pointing to our `UserCache` object.

The call stack for the allocations traced back to a utility function that cached user data for quick access:

```js
// utils/userCache.js
const userCache = new Map();

async function getUser(id) {
  if (userCache.has(id)) return userCache.get(id);
  const user = await db.users.findOne({ _id: id });
  userCache.set(id, user);
  return user;
}
```

At first glance, caching seemed harmless—why not keep user objects around for the duration of the service? The problem was that we never evicted entries, and the cache kept growing as new users placed orders. In a high‑traffic environment, that means unbounded memory growth.

## The Fix: Refactoring the Cache

The solution was to replace the naïve `Map` with an LRU (Least Recently Used) cache that caps the number of entries. I pulled in the lightweight `lru-cache` package, which gives us TTL (time‑to‑live) and size limits out of the box.

```bash
npm install lru-cache
```

Here’s the refactored module:

```js
// utils/userCache.js
const LRU = require('lru-cache');

const options = {
  max: 5000,               // store at most 5,000 users
  ttl: 1000 * 60 * 10,     // entries expire after 10 minutes
  allowStale: false,
  updateAgeOnGet: true,
};

const userCache = new LRU(options);

async function getUser(id) {
  const cached = userCache.get(id);
  if (cached) return cached;

  const user = await db.users.findOne({ _id: id });
  if (user) userCache.set(id, user);
  return user;
}

module.exports = { getUser };
```

A few notes on the changes:

* **`max`** limits the total number of cached users. Once we hit 5 k entries, the least‑recently used ones get evicted automatically.
* **`ttl`** ensures that stale data doesn’t linger forever, which is also important for consistency.
* The cache now returns `undefined` when an entry is missing, prompting a fresh DB fetch.

After deploying the updated service, I watched the heap stabilize around 300 MB, well within our limits. The OOM kills stopped, and the latency dropped slightly because the cache still served the hot users efficiently.

## Lessons Learned

1. **Never Assume “Cache‑Forever” Is Safe** – Caching is a double‑edged sword. If you don’t bound it, you bound the memory usage instead.
2. **Heap Snapshots Are Gold** – Taking a snapshot after reproducing the issue gave me a concrete view of the offending objects. It’s far more reliable than eyeballing logs.
3. **Instrumentation Helps, But It’s Not a Substitute** – Adding `process.memoryUsage` logs showed the trend, but the real culprit only emerged when I inspected the heap.
4. **Choose the Right Tool for the Job** – The built‑in `Map` works for small, static datasets. For anything that can grow, an LRU or TTL cache library saves you from reinventing the wheel.
5. **Automated Alerts Should Include Trends** – A single spike can be noisy, but a steadily rising trend is a red flag. Our monitoring now tracks “heap growth rate” in addition to absolute values.

## Takeaway

Memory leaks in Node.js often hide behind seemingly innocuous patterns—like an unbounded in‑memory cache. By reproducing the issue locally, instrumenting the process, and taking a heap snapshot, you can pinpoint the exact object graph that’s ballooning. Swapping a raw `Map` for a bounded LRU cache resolved the leak in minutes and restored stability to the service. The next time you see your container’s RSS creeping upward, remember to ask: *what am I holding onto that I never release?*
