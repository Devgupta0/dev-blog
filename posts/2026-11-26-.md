When I first shipped a microservice that aggregates data from a public weather API, I was thrilled to see the dashboard light up with live forecasts. That excitement quickly turned to frustration when the service started throwing HTTP 429 “Too Many Requests” errors every few minutes. The API provider enforced a strict **100‑requests‑per‑minute** quota, and my naïve implementation was hammering it with parallel calls. The result? Sporadic failures, angry users, and a whole night of debugging.

In this post I’ll walk you through the exact steps I took to turn that flaky integration into a **graceful, self‑healing** client. We’ll cover:

* Understanding the rate‑limit contract
* Implementing exponential backoff
* Building a retry queue that respects concurrency limits
* Hooking everything together with Axios interceptors

By the end you’ll have a reusable pattern you can drop into any Node.js project that talks to rate‑limited APIs.

## The Root Cause: Ignoring the Rate‑Limit Contract

Most public APIs publish their limits in the documentation, sometimes even in response headers like `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`. My initial code looked something like this:

```js
// naive-fetch.js
const axios = require('axios');

async function fetchAllCities(cities) {
  return Promise.all(
    cities.map(city => axios.get(`https://api.weather.com/v1/${city}`))
  );
}
```

`Promise.all` fires off **all** requests at once, so if `cities` contains 200 entries, I’m instantly sending 200 calls. The API throttles me after the 100‑th request, and the rest explode with 429 errors.

The fix starts with **respecting the contract**: we must throttle our outgoing calls and have a fallback strategy for when we *still* get throttled.

## Designing a Retry Strategy

A robust retry strategy has three pillars:

1. **Detect** – Look for `429` responses or specific rate‑limit headers.
2. **Wait** – Respect the `Retry-After` header if present; otherwise apply exponential backoff.
3. **Retry** – Re‑queue the failed request without blowing up the event loop.

### Exponential Backoff

Exponential backoff is a classic algorithm for dealing with transient failures. The wait time grows exponentially with each retry, typically capped at a max delay. Here’s a tiny helper I wrote:

```js
// backoff.js
function getBackoffDelay(attempt, base = 200, cap = 10000) {
  // base = 200ms, cap = 10s
  const jitter = Math.random() * base;
  const delay = Math.min(cap, base * 2 ** attempt) + jitter;
  return Math.floor(delay);
}
```

The `jitter` randomizes the delay a bit, preventing a “thundering herd” when many requests retry at the same moment.

## Building a Rate‑Limited Axios Wrapper

Axios gives us a clean way to inject interceptors for request/response handling. I created a wrapper that:

* Limits concurrent requests to a configurable `MAX_CONCURRENCY`.
* Retries on 429 with exponential backoff.
* Honors the `Retry-After` header when present.

```js
// rateLimitedAxios.js
const axios = require('axios');
const PQueue = require('p-queue'); // lightweight promise queue
const { getBackoffDelay } = require('./backoff');

const MAX_CONCURRENCY = 5; // keep us well below the API limit
const MAX_RETRIES = 5;

const queue = new PQueue({ concurrency: MAX_CONCURRENCY });

function createRateLimitedClient() {
  const client = axios.create();

  // Response interceptor – handle 429
  client.interceptors.response.use(
    resp => resp,
    async err => {
      const { config, response } = err;
      if (!config || !response) return Promise.reject(err);

      if (response.status === 429 && config.__retryCount < MAX_RETRIES) {
        config.__retryCount = (config.__retryCount || 0) + 1;

        // Respect Retry-After header if the API provides it
        const retryAfter = parseInt(response.headers['retry-after'], 10);
        const delay = Number.isNaN(retryAfter)
          ? getBackoffDelay(config.__retryCount)
          : retryAfter * 1000; // header is seconds

        console.warn(
          `Rate limit hit. Retry #${config.__retryCount} in ${delay}ms`
        );
        await new Promise(res => setTimeout(res, delay));
        return client(config);
      }

      return Promise.reject(err);
    }
  );

  // Wrap the request in the queue to respect concurrency limits
  async function request(config) {
    return queue.add(() => client.request(config));
  }

  return { request };
}

module.exports = { createRateLimitedClient };
```

A few notes on the implementation:

* **`PQueue`** – I chose this tiny library because it gives us a clean FIFO queue with concurrency control.
* **`__retryCount`** – Axios lets us attach custom fields to the request config; we use that to count retries.
* **`Retry-After`** – When the server tells us exactly how long to wait, we honor it; otherwise we fall back to exponential backoff.

## Using the Wrapper in Real Code

Now the original `fetchAllCities` function becomes a lot more disciplined:

```js
// weatherService.js
const { createRateLimitedClient } = require('./rateLimitedAxios');

const client = createRateLimitedClient();

async function fetchCityWeather(city) {
  const url = `https://api.weather.com/v1/${encodeURIComponent(city)}`;
  const { data } = await client.request({ url, method: 'GET' });
  return data;
}

async function fetchAllCities(cities) {
  const results = [];
  for (const city of cities) {
    try {
      const weather = await fetchCityWeather(city);
      results.push({ city, weather });
    } catch (e) {
      console.error(`Failed to fetch ${city}:`, e.message);
    }
  }
  return results;
}
```

Because the queue limits us to **5 concurrent requests**, we stay comfortably under the 100‑req/min ceiling even when `cities` contains thousands of entries. If we ever hit a 429, the interceptor retries with an appropriate delay, making the whole pipeline resilient.

## Real‑World Anecdote: The Night the Queue Saved Us

A few weeks after deploying the new client, our monitoring system flagged a spike in latency during a city‑wide promotion. The promotion drove a burst of 2,000 requests in a single minute. I was on call, coffee in hand, watching the logs explode with “429 Too Many Requests”. 

Instead of panicking, I checked the queue length. It was hovering around 300 – exactly the number of pending jobs waiting for a slot. The backoff logic kicked in, spreading retries over the next 30 seconds. Within a minute the error rate dropped to zero, and the dashboard recovered.

The lesson? **A well‑designed queue not only respects limits, it also smooths traffic spikes**. That night I realized the power of combining concurrency control with exponential backoff – a combo that saved us from a potential outage.
