When I first got the frantic Slack ping from our ops team—*“The Node service is at 95 % RAM, restarting every 5 minutes!”*—I knew I was about to spend a weekend chasing ghosts. The thing is, memory leaks in Node.js feel like a phantom that shows up only when the load spikes, then disappears under test conditions. In this post I’ll walk you through the exact process I used to reproduce, diagnose, and finally squash a leak that was silently draining our server’s memory.

## The Moment I Realized It Was a Leak

We run a fairly straightforward Express API that talks to a PostgreSQL DB, does a bit of data shaping, and returns JSON. Under normal traffic the service stays comfortably under 300 MB of RSS. One evening, after a promotional email blast, the metrics dashboard started showing a steady climb: 500 MB → 800 MB → 1.2 GB, and then the process crashed with an out‑of‑memory (OOM) kill.

My first thought was a runaway query or an unbounded array. I added some quick `console.log` statements to dump the length of any arrays I could find, but nothing looked abnormal. The logs were clean, the DB was fine, and the CPU was idle. That’s when I decided to bring in the heavyweight tools: the Node.js built‑in inspector and Chrome’s DevTools.

## Reproducing the Leak Locally

A leak that only appears under load is hard to catch in a unit test. I wrote a tiny load script that mimics the real traffic pattern:

```js
// load-test.js
const http = require('http');
const CONCURRENCY = 50;
const REQUESTS_PER_CONN = 200;

function fireRequests() {
  for (let i = 0; i < CONCURRENCY; i++) {
    const req = http.request({
      hostname: 'localhost',
      port: 3000,
      path: '/api/expensive',
      method: 'GET'
    }, (res) => {
      // Drain the response so the socket can be reused
      res.resume();
    });

    req.on('error', console.error);
    req.end();
  }
}

// Fire a burst every 100 ms
setInterval(fireRequests, 100);
```

Running this against a local copy of the service while monitoring `process.memoryUsage()` gave me a clear upward trend that matched production. At this point I knew I had a reproducible leak.

## Profiling with the V8 Heap Snapshot

Node ships with a built‑in inspector that you can connect to from Chrome:

```bash
node --inspect-brk index.js
```

Then open `chrome://inspect` and click “Open dedicated DevTools for Node”. In the Memory tab I took a *heap snapshot* before the load started, and another after a few minutes of traffic. The diff highlighted a massive number of `Object` entries that were never being released.

The culprit? A `Map` that we kept around to cache database rows for a few seconds. The cache key was a JSON stringified request payload. It looked innocent, but under heavy load we were creating a *new* string for each request, and the cache never evicted anything because the TTL logic was never fired.

## Fix #1: Use a Proper LRU Cache

The first thing I did was replace the ad‑hoc `Map` with an LRU (Least Recently Used) cache library that automatically evicts old entries:

```js
// cache.js
const LRU = require('lru-cache');

const cache = new LRU({
  max: 5000,               // max 5k items
  ttl: 1000 * 60 * 2,      // 2 minutes per entry
  ttlAutopurge: true       // automatically purge expired entries
});

module.exports = {
  get: (key) => cache.get(key),
  set: (key, value) => cache.set(key, value)
};
```

Now the cache respects a hard limit and a TTL, ensuring old payload strings are garbage‑collected.

## Fix #2: Avoid Heavy Stringification

Even with an LRU, constantly stringifying objects for keys is expensive. I switched to a deterministic hashing function (MurmurHash) that works on the raw object:

```js
// hashKey.js
const murmur = require('murmurhash-js');

function makeCacheKey(obj) {
  // Sort keys to guarantee deterministic output
  const sorted = Object.keys(obj).sort().reduce((acc, k) => {
    acc[k] = obj[k];
    return acc;
  }, {});
  return murmur.hash(JSON.stringify(sorted)).toString(16);
}

module.exports = makeCacheKey;
```

Now each request produces a short 8‑character hex string instead of a multi‑kilobyte JSON blob.

## Verifying the Fix

After swapping the cache implementation and the hashing logic, I reran the load script. The heap snapshot after 5 minutes showed almost no growth—just the expected baseline usage. I also added a simple health endpoint that reports `process.memoryUsage().heapUsed` so we can keep an eye on it in production.

```js
// health.js
app.get('/health/memory', (req, res) => {
  const { heapUsed, heapTotal } = process.memoryUsage();
  res.json({ heapUsed, heapTotal });
});
```

Deploying the change to staging, we ran the same traffic burst that previously killed the service. The memory stayed flat at ~350 MB and the service continued serving requests without a hiccup.

## Lessons Learned

1. **Never trust “in‑memory cache” as a free lunch** – even a small TTL bug can explode under load.  
2. **Always profile under realistic traffic** – synthetic unit tests rarely reveal leaks that only appear with concurrency.  
3. **Prefer battle‑tested data structures** – the `lru-cache` library handles eviction, TTL, and size limits for you, reducing the chance of human error.  
4. **Make cache keys cheap** – hashing raw objects is far cheaper than repeatedly stringifying large payloads.

## Takeaway

Memory leaks in Node.js are often the result of a simple oversight—an unbounded collection, a forgotten timer, or an expensive key‑generation routine. By reproducing the problem with a realistic load generator, taking V8 heap snapshots, and swapping ad‑hoc structures for proven libraries, you can turn a nightmarish OOM crash into a stable, predictable service. The next time your metrics start creeping upward, remember: the leak is probably hiding in plain sight, waiting for the right traffic pattern to reveal itself. Happy debugging!
