How I Stopped My Node.js App From Leaking Memory with Event Emitters

2026-11-12Devguptanodejs memory-leak eventemitters performance

---

When I first rolled out a new real‑time notification service for our SaaS product, the metrics looked great: sub‑millisecond latency, zero downtime, and a happy engineering team. A few weeks later, the same service started crashing with FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed - JavaScript heap out of memory. My initial instinct was to increase the container memory limit, but the root cause was far more insidious—it was a memory leak caused by stray EventEmitter listeners.

The Anatomy of an EventEmitter Leak

Node’s EventEmitter is a powerful abstraction for decoupling components. You can emit events from one part of your code and let any number of listeners react. The catch? Listeners are never automatically removed. If you keep adding listeners without cleaning them up, you’ll eventually saturate the heap.

Typical warning signs:

  • The process logs MaxListenersExceededWarning (default is 10 listeners per event).
  • Heap snapshots show an ever‑growing number of EventEmitter objects.
  • GC pauses start to increase noticeably.
In my case, the warning appeared only intermittently because the listeners were being attached inside a request handler that ran for each WebSocket connection. Over time, each new connection added a fresh listener to a global emitter that was never torn down when the socket closed.

Reproducing the Leak Locally

Before diving into the production logs, I built a minimal reproduction to confirm the hypothesis:

// leak-demo.js
const { EventEmitter } = require('events');
const http = require('http');

const globalBus = new EventEmitter();


function handleRequest(req, res) {
  // Each request adds a new listener for the 'ping' event
  globalBus.on('ping', () => {
    console.log(Ping received from ${req.socket.remoteAddress});
  });


// Simulate a response
  res.end('OK');
}


http.createServer(handleRequest).listen(3000);
console.log('Server listening on :3000');

Running this script and hammering it with ab -n 10000 -c 100 http://localhost:3000/ quickly blew the heap. The console printed MaxListenersExceededWarning after the 11th request, confirming that listeners were stacking up per request.

Strategies to Prevent Leaks

1. Scope Listeners to Their Lifecycle

Instead of attaching listeners to a global emitter, bind them to objects that have a clear lifecycle (e.g., a WebSocket connection object). When the object is disposed, remove its listeners.

// websocket-service.js
const { EventEmitter } = require('events');

class Client extends EventEmitter {
  constructor(ws) {
    super();
    this.ws = ws;


// Listen for a custom event that only this client cares about
    this.on('notify', this.sendNotification);
    
    ws.on('close', () => this.cleanup());
  }


sendNotification(payload) {
    this.ws.send(JSON.stringify(payload));
  }


cleanup() {
    // Remove all listeners attached to this instance
    this.removeAllListeners();
    console.log('Client cleaned up');
  }
}

By making each client its own emitter, the cleanup method guarantees that no stray listeners linger after the socket disconnects.

2. Use once When Appropriate

If a listener only needs to react a single time, register it with once. Node will automatically deregister after the first invocation.

globalBus.once('init', () => {
  console.log('Initialization complete');
});

3. Explicitly Remove Listeners

When you really need to detach a listener, keep a reference to the handler function so you can call removeListener (or off in newer Node versions).

function onData(data) {
  console.log('Data:', data);
}

// Attach
globalBus.on('data', onData);


// Later, when the consumer is done
globalBus.off('data', onData);

4. Monitor Listener Count Programmatically

Node exposes emitter.listenerCount(eventName). Hook this into health checks to alert you before hitting the warning threshold.

setInterval(() => {
  const count = globalBus.listenerCount('ping');
  if (count > 8) {
    console.warn(High listener count for 'ping': ${count});
  }
}, 30_000);

Refactoring the Real‑World Service

Armed with these patterns, I refactored the notification service:

  1. Created a per‑connection emitter (Client class) that wrapped each WebSocket.
  2. Moved all global listeners that only needed to act on a specific client to that client’s instance.
  3. Added a health‑check interval that logs listener counts for critical events.
  4. Set maxListeners to a sane value (globalBus.setMaxListeners(20)) to surface abnormal spikes early.
After deploying the changes, heap usage stabilized, and the MaxListenersExceededWarning vanished. The service now runs comfortably within its 256 MiB memory limit.

Tools for Hunting Down Leaks

  • node --inspect + Chrome DevTools – Take heap snapshots and filter by EventEmitter.
  • clinic.js – The clinic heapprofile command visualizes memory growth over time.
  • process.memoryUsage() – Log RSS, heapTotal, and heapUsed at regular intervals to spot trends.

Lessons Learned

  • Never trust “it works for now”. EventEmitter warnings are easy to ignore because they’re just console messages, but they’re often the first sign of a leak.
  • Tie resources to lifecycles. If you spin up a listener, you must also spin down that listener when the owning object is done.
  • Automate detection. A simple setInterval that checks listenerCount can save you hours of debugging later.

Takeaway

  • Listeners are not garbage‑collected automatically – you must remove them explicitly or bind them to objects that get disposed.
  • Scope listeners to the entity that owns them (e.g., a WebSocket client) and clean up in its close/destroy callback.
  • Use once, off, and removeAllListeners strategically to keep the emitter’s internal list tidy.
  • Instrument your app to surface listener counts and heap growth before they become fatal.
By treating EventEmitters like any other resource—acquire, use, release—you’ll keep your Node.js services lean, performant, and free of those dreaded “heap out of memory” crashes. Happy coding!
