Why Empty Strings Matter: Handling '' in JavaScript Applications

2026-11-12Devguptajavascript strings best-practices

When I first started writing a small Node‑API for a client‑side form, I assumed an empty string ("") was the same as “no value”. Fast forward a week, the API started returning 500 errors for seemingly valid submissions. The culprit? An empty string sneaking past my validation logic and breaking a downstream SQL query. This post is the story of that bug, why empty strings are a hidden gotcha in JavaScript, and a set of practical patterns you can copy‑paste into your own codebase.

The subtle difference between null, undefined, and ""

JavaScript’s loosely typed nature gives us three “nothing” values that look similar but behave very differently:

| Value | Type | Truthiness | Typical source | |--------------|-----------|------------|----------------| | null | object | falsy | Explicit “no value” | | undefined | undefined | falsy | Missing property / uninitialized variable | | "" (empty) | string | falsy | User typed nothing, trimmed input, or default param |

All three coerce to false in a boolean context, but they’re not interchangeable. For example:

if (value) {
  // This block runs for any non‑empty string, non‑zero number, non‑null object, etc.
}

If value is "", the if guard fails—exactly like null or undefined. The problem appears when you expect a string and later call string methods without confirming the value really is a string.

Real‑world bug: Empty string vs. missing field

The scenario

Our front‑end used a simple for a “promo code”. The back‑end API expected either a valid promo code or nothing at all. The validation middleware looked like this:

function validatePromo(req, res, next) {
  const { promo } = req.body;

// We thought this would catch both null and empty strings
  if (!promo) {
    return next(); // No promo, fine
  }


// Otherwise, look it up in the DB
  db.findPromo(promo)
    .then(p => {
      if (!p) throw new Error('Invalid promo');
      req.promo = p;
      next();
    })
    .catch(err => res.status(400).json({ error: err.message }));
}

The user left the field blank, the browser sent promo: "". The !promo guard evaluated to true, so the request passed through. No problem yet.

But a few days later a marketing partner added a default promo code to the UI that was an empty string (they thought “empty = no promo”). The front‑end started sending promo: "" and a hidden field promoSource: "partner".

Our middleware still considered !promo true, but downstream code assumed req.promo would be defined if promoSource existed:

if (req.body.promoSource && !req.promo) {
  // Oops – we try to concatenate a non‑existent object later
  log.error('Missing promo object for source', req.body.promoSource);
}

When the logger attempted to stringify req.promo, Node threw TypeError: Cannot read property 'code' of undefined. The 500 error surfaced in production.

The root cause

The root cause was treating an empty string as “no promo” while other parts of the code treated any presence of promoSource as a signal that a promo must exist. The mismatch between null/undefined and "" caused the bug.

Detecting an empty string reliably

1. Use === "" for strict emptiness

If you need to differentiate an empty string from null or undefined, compare directly:

if (value === "") {
  // It's an empty string, not null/undefined
}

2. Combine type‑check with length

A more defensive pattern:

function isNonEmptyString(val) {
  return typeof val === "string" && val.length > 0;
}

Now isNonEmptyString(null) → false, isNonEmptyString(undefined) → false, isNonEmptyString("") → false.

3. Normalise inputs early

A common technique is to coerce null/undefined into an empty string once at the boundary of your system:

function normalizeString(input) {
  return input == null ? "" : String(input);
}

Then downstream code can safely call string methods without guard clauses, because you’ve guaranteed a string type (though it may still be empty).

Sanitising user input: Trim, default, and validate

User‑entered text often contains leading/trailing whitespace that makes an empty string look “non‑empty”. Always trim:

function cleanInput(raw) {
  const trimmed = raw == null ? "" : String(raw).trim();
  return trimmed; // now "" truly means “nothing typed”
}

If your business logic treats “no value” differently from an empty string, decide on a canonical representation (usually null) and convert early:

function emptyToNull(str) {
  return str === "" ? null : str;
}

Defensive coding checklist

  1. Never rely on truthiness alone for string presence. Use a helper like isNonEmptyString.
  2. Normalize at the API boundary – turn null/undefined into "" or null consistently.
  3. Trim whitespace before validation.
  4. Document expectations in TypeScript or JSDoc so teammates know whether a field may be empty.
  5. Write unit tests for edge cases: null, undefined, "", " ", and valid strings.

Example: A robust validation middleware

Below is a compact version of the promo‑code validator that avoids the earlier pitfall:

// utils.js
export function isNonEmptyString(val) {
  return typeof val === "string" && val.trim().length > 0;
}

// promoMiddleware.js
import { isNonEmptyString } from "./utils.js";


export async function validatePromo(req, res, next) {
  const rawPromo = req.body.promo; // could be undefined, null, or ""


// Normalise & trim
  const promo = typeof rawPromo === "string" ? rawPromo.trim() : "";


if (!isNonEmptyString(promo)) {
    // No promo supplied – explicitly set null for downstream clarity
    req.promo = null;
    return next();
  }


try {
    const promoRecord = await db.findPromo(promo);
    if (!promoRecord) {
      return res.status(400).json({ error: "Invalid promo code" });
    }
    req.promo = promoRecord;
    next();
  } catch (err) {
    console.error("Promo validation error:", err);
    res.status(500).json({ error: "Server error while validating promo" });
  }
}
