When I first started working on a large‑scale Node.js microservice, I thought I’d nailed the testing strategy: **Jest** for unit tests, **SuperTest** for integration, and a nightly **GitHub Actions** workflow that ran everything on a clean Docker image. For weeks the green checkmarks were reassuring—until one morning the CI started flickering red and green on the same commit. The failure was nondeterministic, sometimes passing, sometimes crashing with a timeout error. My team called it a *flaky test* and, honestly, we didn’t know how to tame it.

In this post I’ll walk you through the exact steps I took to diagnose and eliminate the flakiness, the tooling that helped, and a repeatable process you can apply to any language or CI system.

## The First Clue: Intermittent Timeout

The offending test was an integration test that hit an in‑memory SQLite database, performed a series of HTTP requests against the service, and then asserted on the final response. The error looked like this:

```
Error: Timeout - Expected response within 2000ms, but got 5874ms
```

At first glance it seemed like a performance regression, but the test passed locally on my laptop every time. The only difference was the CI environment: a fresh Docker container with limited CPU shares. My first thought was “maybe the container is starved”, but adding `--cpus="2"` to the runner didn’t fix anything.

## Step 1: Reproduce Locally in a “CI‑ish” Environment

The most reliable way to debug flakiness is to reproduce it under the same constraints. I spun up a Docker container that mimicked the CI image:

```bash
docker run -it --rm \
  -v $(pwd):/app \
  -w /app \
  node:20-slim \
  sh -c "npm ci && npm test"
```

Running the test suite inside that container produced the same intermittent failure. Now I had a reproducible environment.

## Step 2: Add Deterministic Logging

The next thing I did was sprinkle the test with timestamps and resource usage logs. I used `process.hrtime.bigint()` to capture nanosecond precision and printed the duration of each request:

```js
const start = process.hrtime.bigint();
await request(app).post('/api/v1/items').send(payload);
const end = process.hrtime.bigint();
console.log('POST /items took', Number(end - start) / 1e6, 'ms');
```

When the test flaked, the logs showed a spike in the time it took to acquire a database lock:

```
[2026-11-19T12:03:45.123Z] POST /items took 1542 ms
[2026-11-19T12:03:45.124Z] DB lock acquisition took 4231 ms
```

That hinted at a race condition inside SQLite.

## Step 3: Isolate the Shared Resource

SQLite in memory databases are process‑local, but our test suite spun up multiple parallel Jest workers (`maxWorkers: 4`). Each worker created its own in‑memory DB, yet they all pointed to the same file path (`:memory:`) because of how the test helper imported the DB module. In effect, the workers were sharing the same underlying SQLite instance, leading to lock contention.

The fix was simple: ensure each worker gets a truly isolated database. I rewrote the DB initialization to generate a unique file per worker:

```js
// db.js
import sqlite3 from 'sqlite3';
import { v4 as uuid } from 'uuid';
import path from 'path';
import os from 'os';

export function createTestDb() {
  const dbPath = path.join(os.tmpdir(), `test-db-${uuid()}.sqlite`);
  return new sqlite3.Database(dbPath);
}
```

Now each Jest worker creates its own temporary file, and the contention vanished.

## Step 4: Verify the Fix in CI

After updating the helper, I reran the entire CI pipeline. The flaky test passed consistently for the next 20 builds. I also added a “smoke” job that runs the integration suite with a deliberately low timeout (`--detectOpenHandles`) to surface any hidden deadlocks early.

## Step 5: Prevent Future Flakiness

Even with the immediate issue solved, I wanted a safety net:

1. **Run tests in serial when they touch shared resources** – Use Jest’s `maxWorkers=1` for such suites, or tag them with a custom runner.
2. **Add a “flaky‑detector” job** – Run the test suite a few times in a row (`npm test -- --runInBand`) and fail if any iteration diverges.
3. **Monitor CI resource usage** – Export CPU/memory metrics and set alerts if a job exceeds thresholds.

I codified these steps into a shared `ci-utils` package so any new project can import the same patterns.

## The Human Side: When Debugging Becomes a Lesson

I remember the moment the CI turned red on a Friday afternoon. My manager asked, “Is that a real bug or just a CI hiccup?” I could’ve brushed it off as a transient glitch, but I chose to dig deeper. The process forced me to think about **test isolation**, something I’d taken for granted. It also reminded me that CI isn’t just a black box that runs commands; it’s a reproducible environment that can expose hidden concurrency bugs you’d never see locally.

That experience reshaped my approach to testing: I now write a short “environment checklist” for every new test suite, and I treat flaky tests as a signal to improve architecture rather than an annoyance to be ignored.

## Tools and Techniques That Made a Difference

| Tool | Why It Helped |
|------|---------------|
| **Docker** | Replicated CI environment locally |
| **Jest `--detectOpenHandles`** | Exposed lingering async operations |
| **`process.hrtime.bigint()`** | High‑resolution timing for pinpointing bottlenecks |
| **UUID‑based temp files** | Guaranteed isolation of SQLite instances |
| **GitHub Actions `jobs.<job>.strategy.matrix`** | Allowed me to run the same test suite with different concurrency settings |

## Common Pitfalls When Dealing With Flaky Tests

1. **Assuming the CI runner is at fault** – Often the test itself is nondeterministic.
2. **Adding more retries** – This masks the problem and inflates CI time.
3. **Changing timeouts without root cause analysis** – Leads to brittle suites that can still break under load.

Instead, follow a systematic approach: reproduce, instrument, isolate, fix, and guard.
