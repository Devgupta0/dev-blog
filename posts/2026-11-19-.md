When I first noticed our production API started choking on a Friday evening, I thought it was just a traffic spike. By midnight the container was hitting 95 % RAM usage, the latency was climbing, and the health checks started failing. The alarm bells were ringing, but the logs showed nothing abnormal. It turned out we were dealing with a **silent memory leak** that had been creeping in for weeks.

In this post I’ll share exactly how I tracked down the culprit, the tools that saved me hours of guess‑work, and the code refactor that finally put the leak to rest. If you’ve ever stared at a “out of memory” crash without a clear stack trace, this walk‑through should feel familiar.

## The First Clue: Metrics Gone Crazy

Our monitoring stack (Prometheus + Grafana) gave us the first hint. The `process_resident_memory_bytes` metric for the service started a slow upward drift around the time we introduced a new feature: a background job that periodically pulls data from a third‑party API and caches the result in memory.

I added a quick annotation to the Grafana graph to mark the feature rollout. The memory curve didn’t spike instantly; instead it rose a few megabytes every minute. That pattern screams *leak* rather than a bursty load spike.

## Reproducing the Issue Locally

Before I could start poking around in production, I needed a reproducible scenario. I spun up a local Docker container mirroring the production image and ran a simple script that hit the endpoint continuously:

```bash
#!/usr/bin/env bash
while true; do
  curl -s http://localhost:3000/api/v1/resource > /dev/null
  sleep 0.1
done
```

After a couple of minutes the container’s RSS (resident set size) started climbing just like in prod. With a reproducible test, I could safely attach debuggers and profiling tools.

## Taking a Heap Snapshot

Node.js ships with built‑in V8 heap snapshot capabilities. I used the `--inspect` flag and Chrome DevTools to take a snapshot after the process had been running for a while.

1. Start the service with `node --inspect-brk index.js`.
2. Open `chrome://inspect` and connect to the remote target.
3. In the *Memory* tab, take a *Heap snapshot*.

The snapshot showed a massive number of `Array` objects, each holding dozens of tiny JSON payloads. The *retainers* view pointed back to a module called `cache.js`. That was a big hint.

## Digging Into the Cache Implementation

Our caching layer was a thin wrapper around a plain JavaScript `Map`. The code looked like this:

```js
// cache.js
class SimpleCache {
  constructor(ttlMs) {
    this.ttl = ttlMs;
    this.store = new Map();
  }

  set(key, value) {
    const expiresAt = Date.now() + this.ttl;
    this.store.set(key, { value, expiresAt });
  }

  get(key) {
    const entry = this.store.get(key);
    if (!entry) return undefined;

    if (Date.now() > entry.expiresAt) {
      this.store.delete(key);
      return undefined;
    }
    return entry.value;
  }
}
module.exports = SimpleCache;
```

At first glance it seemed fine—entries are removed once they expire. The problem? **Expiration only happens on a `get` call**. If a key never gets accessed again, its timer never fires, and the entry lives forever. Our background job was populating the cache with fresh data for thousands of IDs, many of which were never requested again.

## Fix #1: Periodic Sweep

I added a simple sweeper that runs every minute to purge stale entries:

```js
class SimpleCache {
  constructor(ttlMs, sweepIntervalMs = 60_000) {
    this.ttl = ttlMs;
    this.store = new Map();

    // Start periodic cleanup
    this.sweeper = setInterval(() => this._sweep(), sweepIntervalMs);
    this.sweeper.unref(); // Don't block process exit
  }

  set(key, value) {
    const expiresAt = Date.now() + this.ttl;
    this.store.set(key, { value, expiresAt });
  }

  get(key) {
    const entry = this.store.get(key);
    if (!entry) return undefined;

    if (Date.now() > entry.expiresAt) {
      this.store.delete(key);
      return undefined;
    }
    return entry.value;
  }

  _sweep() {
    const now = Date.now();
    for (const [key, { expiresAt }] of this.store.entries()) {
      if (now > expiresAt) this.store.delete(key);
    }
  }

  // Graceful shutdown helper
  close() {
    clearInterval(this.sweeper);
  }
}
```

The sweeper ensures that even untouched keys get cleaned up. After deploying this change, memory usage plateaued for the first few hours of the test run.

## Fix #2: Use LRU Instead of Bare Map

While the sweeper solved the leak, the cache still grew to an unwieldy size under heavy load. I swapped the custom implementation for the battle‑tested `lru-cache` npm package, which handles both TTL and max‑size eviction out of the box.

```js
const LRU = require('lru-cache');

const cache = new LRU({
  max: 10_000,               // maximum number of items
  ttl: 5 * 60 * 1000,        // 5 minutes
  updateAgeOnGet: true,      // refresh TTL on read
  allowStale: false
});

// Usage remains the same
cache.set(userId, userProfile);
const profile = cache.get(userId);
```

The library internally keeps a doubly‑linked list to efficiently evict the least‑recently‑used items, and it automatically purges expired entries on each operation. After swapping, the memory curve flattened even more, and we now have a predictable upper bound on RAM usage.

## Verifying the Fix with Load Testing

To be sure the leak was truly gone, I ran a short load test with `k6`:

```js
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  vus: 50,
  duration: '5m',
};

export default function () {
  http.get('http://localhost:3000/api/v1/resource');
  sleep(0.1);
}
```

During the test I monitored `process_resident_memory_bytes` and `process_heap_used_bytes`. Both metrics stayed flat, hovering around 120 MB—the baseline for the container. No more upward drift.

## Lessons Learned

1. **Never trust “lazy” eviction.** Relying on reads to trigger cleanup can leave dead entries hanging forever.  
2. **Heap snapshots are your friend.** Even a single snapshot can point you to the offending module.  
3. **Prefer battle‑tested libraries for common patterns.** Implementing an LRU cache from scratch is easy to get wrong; a well‑maintained npm package saves you bugs and future maintenance.  
4. **Add observability early.** A simple Grafana metric gave us the first clue before any alert fired.

## Takeaway

Memory leaks in JavaScript are often *silent*—they don’t crash immediately but slowly erode your service’s stability. By combining runtime metrics, heap snapshots, and a disciplined approach to cache eviction, you can catch and fix leaks before they become production incidents. The next time you see a gradual RAM climb, remember: the problem is probably sitting in a piece of code that *should* clean up but never does. A quick sweep, a proper eviction strategy, or a proven library can turn a leaking nightmare into a stable, predictable service. Happy debugging!
