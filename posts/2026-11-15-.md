When I first saw the heap size of my Node.js microservice creep past 2 GB overnight, my heart sank. The service was a thin wrapper around a third‑party API, and I’d never run into any stability issues before. Yet the logs were spitting out `FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed - JavaScript heap out of memory`. I’d spent the previous week polishing a new feature, so the last thing I wanted was to dig into a performance nightmare. This post is the story of how I diagnosed the leak, why my initial guesses were wrong, and the concrete steps that finally put the problem to rest.

## The First Clues: Metrics & Logs

The first thing I did was look at the monitoring dashboards. The CPU was fine, but the **heap used** metric showed a steady upward slope, roughly 150 MB every hour. No spikes, just a smooth climb. That pattern hinted at a *slow‑drip* leak rather than a one‑off allocation burst.

I also enabled `--trace-gc` in the start script:

```bash
node --trace-gc server.js
```

The GC logs confirmed my suspicion—*major* collections were happening more frequently, and each one freed less memory than the previous. At this point I knew I needed a deeper look at what objects were living in the heap.

## Taking a Snapshot with Chrome DevTools

Node ships with the `--inspect` flag, which lets you attach Chrome DevTools to a running process. I started the service with:

```bash
node --inspect=0.0.0.0:9229 server.js
```

Then I opened `chrome://inspect` and connected to the remote target. From the **Memory** panel I took a *Heap snapshot* after the service had been running for an hour. The snapshot showed a massive number of `Array` objects, each holding dozens of tiny objects. The **Retainers** view revealed that the culprit was a **global cache object** that I had introduced in a previous sprint.

## The (False) Hero: Global Cache

In the rush to improve latency I’d added a simple in‑memory cache:

```js
// cache.js
const cache = new Map();

module.exports = {
  get: (key) => cache.get(key),
  set: (key, value) => cache.set(key, value),
  clear: () => cache.clear()
};
```

Every API response was cached for 5 minutes:

```js
// service.js
const { get, set } = require('./cache');

async function fetchUser(id) {
  const cached = get(id);
  if (cached) return cached;

  const user = await thirdPartyApi.getUser(id);
  set(id, user); // <-- leak suspect
  return user;
}
```

At first glance, this looked fine. But the service was **stateless** and handled thousands of distinct user IDs per day. The cache never evicted entries—`clear()` was never called, and there was no TTL logic. The Map kept growing, and each entry held the full user payload (often ~10 KB). Multiply that by tens of thousands of users, and the heap ballooned quickly.

## Why My Initial Fix Didn’t Work

My first attempt was to add a manual `clear()` call after each request, hoping that would keep the Map small:

```js
set(id, user);
clear(); // tried to reset the cache
```

That obviously wiped out the cache after every request, which defeated the whole point of caching and introduced a performance regression. The heap size stopped growing, but the service became slower, and the logs started complaining about rate‑limit errors from the third‑party API.

The lesson? **Don’t sacrifice a core requirement (caching) just to stop a leak.** Instead, implement a proper eviction strategy.

## Implementing an LRU Cache

I swapped the naïve `Map` for an LRU (Least Recently Used) cache library, `lru-cache`, which gives you size‑based eviction out of the box:

```bash
npm install lru-cache
```

```js
// cache.js
const LRU = require('lru-cache');

const options = {
  max: 5 * 1024 * 1024, // 5 MB total size
  ttl: 1000 * 60 * 5,   // 5 minutes TTL per entry
  sizeCalculation: (value, key) => {
    // Rough estimate: key length + JSON string length
    return Buffer.byteLength(key) + Buffer.byteLength(JSON.stringify(value));
  }
};

const cache = new LRU(options);

module.exports = {
  get: (key) => cache.get(key),
  set: (key, value) => cache.set(key, value),
  // No explicit clear needed; LRU handles it
};
```

A few things changed:

1. **Size‑based eviction** (`max`) ensures the total memory used by the cache never exceeds 5 MB.
2. **TTL** (`ttl`) automatically removes stale entries after five minutes.
3. **sizeCalculation** gives the cache a realistic sense of how much memory each entry consumes.

After deploying this change, the heap usage plateaued around 300 MB, well within the container limits. The service retained the performance boost from caching while staying healthy.

## Verifying the Fix with Heap Snapshots

To be absolutely sure, I repeated the heap snapshot workflow after the new version had been running for a few hours. The **Dominators** view now listed the `LRUCache` itself as a relatively small node, and the number of `Array` objects had dropped dramatically. The GC logs showed major collections freeing a healthy chunk of memory each time.

I also added a simple health check endpoint that reports the current cache size:

```js
app.get('/health/cache', (req, res) => {
  const { cache } = require('./cache');
  res.json({
    entries: cache.size,
    totalSize: cache.calculatedSize,
    maxSize: cache.max
  });
});
```

Monitoring this endpoint gave me early visibility into any future cache‑related growth.

## A Few Extra Tips for Future Leaks

- **Never trust “global” objects** without a clear lifecycle. If you need a cache, give it a bounded policy.
- **Use `process.memoryUsage()`** in a periodic health check to catch abnormal growth early.
- **Automate heap snapshot collection** in CI for regressions: tools like `memlab` can compare snapshots and flag size anomalies.
- **Prefer libraries** that already implement eviction strategies over rolling your own ad‑hoc caches.

## Lessons Learned

- A memory leak can hide behind a seemingly innocent optimization.
- Relying on manual `clear()` calls is brittle; let the data structure manage its own lifecycle.
- Heap snapshots are invaluable; they turn “I see the heap growing” into “I know exactly what’s growing”.

## Takeaway

- **Identify** the leak early with metrics and GC logs.  
- **Snapshot** the heap to pinpoint the offending objects.  
- **Replace** unbounded data structures (like a raw `Map`) with bounded alternatives (LRU cache, TTL, size caps).  
- **Validate** the fix with another snapshot and continuous monitoring.  

By giving the cache a disciplined eviction policy, I turned a crashing service into a stable, performant component—without sacrificing the latency gains that caching provides. If you ever find yourself staring at an ever‑growing heap, remember: the fix is often as simple as adding a limit. Happy debugging!
