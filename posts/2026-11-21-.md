When I first rolled out a new feature for our real‑time analytics service, the API started to **slow down** after a few hours of traffic. The CPU stayed low, but the process memory kept climbing until the container was OOM‑killed. I spent a sleepless night watching the `RSS` metric creep up, and that’s when I realized I was staring at a classic memory‑leak scenario.

Below is the step‑by‑step method I used to **find**, **measure**, and **fix** the leak. Feel free to copy the snippets, adapt the workflow to your stack, and—most importantly—save yourself a late‑night debugging session.

## The Symptoms: When “It Works Locally” Becomes “It Crashes in Production”

| Metric | Expected | Observed |
|--------|----------|----------|
| CPU %  | < 30%    | ~10% (steady) |
| Heap Used (MB) | 150‑200 | 350 → 1 GB (growing) |
| Requests/sec | 1 200 | 1 200 (but latency spikes) |
| Container restarts | 0 | 4 per hour |

The key clue was **stable CPU** while **heap usage kept ballooning**. That pattern almost always points to objects being retained longer than they should.

## Tooling Up: Heap Snapshots & the Chrome DevTools Profiler

Node.js ships with the `--inspect` flag, which lets you attach Chrome DevTools to a running process. I used the following command to start the service in a way that allowed live inspection:

```bash
node --inspect-brk=0.0.0.0:9229 index.js
```

- `--inspect-brk` pauses execution on the first line, giving me a chance to set breakpoints before any traffic hits.
- `0.0.0.0:9229` makes the debugger reachable from my laptop (via port‑forwarding in Kubernetes).

Once attached, I navigated to the **Memory** panel, clicked **Take snapshot**, and let the service run for a few minutes under load. I repeated the snapshot after 30 minutes and compared the two.

### What the Snapshot Tells You

The **Comparison** view highlights *detached DOM trees*, *closure scopes*, and **Retained Size** per object type. The biggest surprise was a **`Set`** that kept growing, holding onto thousands of request‑specific objects.

## Pinpointing the Leak: The Culprit Was a Global Cache

Our codebase had a tiny utility that cached user sessions for quick lookup:

```js
// utils/sessionCache.js
const sessionCache = new Set();

function addSession(session) {
  sessionCache.add(session);
}

// Called on every incoming request
module.exports = { addSession };
```

At first glance, a `Set` seemed harmless—just a collection of active sessions. However, we **never removed** sessions after they expired. The garbage collector could not reclaim any of those objects because the `Set` kept a strong reference.

### Why It Went Unnoticed Locally

During local development we only processed a handful of requests, so the set never grew beyond a few dozen entries. In production, with thousands of concurrent users, the set ballooned and ate up memory.

## Fixing the Leak: A TTL‑Based Cache

I replaced the naïve `Set` with a **time‑to‑live (TTL) map** that automatically evicts stale entries. I used the `lru-cache` library because it already handles expiration, max size, and provides useful stats.

```bash
npm i lru-cache
```

```js
// utils/sessionCache.js
const LRU = require('lru-cache');

const cache = new LRU({
  max: 10_000,               // upper bound on entries
  ttl: 1000 * 60 * 15,       // 15 minutes
  dispose: (key, value) => {
    // optional cleanup if needed
    console.log(`Session ${key} evicted`);
  }
});

function addSession(sessionId, sessionObj) {
  cache.set(sessionId, sessionObj);
}

function getSession(sessionId) {
  return cache.get(sessionId);
}

module.exports = { addSession, getSession };
```

Key points:

- **`max`** prevents unbounded growth.
- **`ttl`** ensures each entry expires after 15 minutes of inactivity.
- **`dispose`** hook can be used for extra cleanup (e.g., closing DB connections).

## Verifying the Fix

After deploying the new cache, I repeated the heap‑snapshot workflow:

1. **Snapshot 0** (cold start): 160 MB.
2. **Snapshot 30 min** (steady load): 165 MB → **stable**.
3. **RSS** stayed under 250 MB for 24 h.

The memory profile flattened, confirming that the leak was gone.

## A Quick Checklist for Future Leak Hunting

| ✅ | Checklist Item |
|---|-----------------|
| ✅ | Enable `--inspect` and capture heap snapshots at regular intervals. |
| ✅ | Compare snapshots: look for objects whose retained size grows monotonically. |
| ✅ | Trace the allocation stack (DevTools shows the source line). |
| ✅ | Verify that long‑lived collections (maps, sets, caches) have eviction policies. |
| ✅ | Add unit tests that simulate high‑load scenarios and assert memory usage stays bounded (e.g., using `memwatch-next`). |

## Lessons Learned (and a Tiny Anecdote)

During the early debugging stages I tried to **restart the container** every 10 minutes as a band‑aid. It worked temporarily, but the OOM kill kept reappearing. One night, after a marathon of `ps aux` and `top`, I realized I’d been looking at **CPU** while the real problem lived in **heap**. The moment I attached Chrome DevTools, the `Set` jumped out like a neon sign.

The moral? **Never trust a single metric**. Memory problems hide behind stable CPU and low latency until they explode.

## Takeaway

- **Heap snapshots** are your best friend for spotting hidden leaks.  
- Global collections without eviction (e.g., raw `Set`/`Map`) are common culprits.  
- Use proven caching libraries (`lru-cache`, `node-cache`) that enforce size/TTL limits.  
- Automate memory‑profile checks in CI to catch regressions early.

By integrating these practices into your development workflow, you’ll spend less time firefighting OOM crashes and more time shipping features—while keeping your Node.js services lean, performant, and reliable. Happy debugging!
